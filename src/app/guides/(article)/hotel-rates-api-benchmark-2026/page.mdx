# Hotel rates API benchmark 2026: seven APIs, one hotel, real calls

<GuideDates published="2026-10-07" updated="2026-10-12" />

**Short answer:** I sent the same Lisbon search and the same Rome hotel to seven hotel price
APIs on 2026-10-07, three runs each. StayAPI, SearchApi and HasData answered a Booking.com
destination search in 1.1 to 2.1 seconds and SerpApi's Google Hotels engine in 2.4. Mine,
FlightPowers, took 7.9, slower than every API here except an Apify scraper run, which took 75. The bigger
finding was the price: the same room came back as $915 or as $1,057 depending on whether the
API put Rome's VAT and city tax into the number it called the price.

I run FlightPowers and sell one of the APIs in this test, so read my rows as a vendor
measuring himself. Every number below is from a call I made that afternoon, apart from one dated
re-check of the sort fix, with the raw response kept, and the list of where mine loses
is longer than the list of where it wins.

## How I tested

Same questions, same dates, every API: check-in **2026-11-20**, check-out **2026-11-23**
(3 nights), 2 adults, 1 room, prices in USD.

1. **Destination search:** Lisbon, sorted by price wherever the API can sort.
2. **One named hotel:** Hotel Artemide, Rome. I meant to use Hotel Sant'Angelo, but it was
   sold out on Booking.com for those dates, so everyone got Artemide.
3. **The same hotel seen from two countries,** Germany and the US, wherever the API has an input
   for it.

Wall time is from the request leaving to the last byte of the answer, from one server in the US,
three runs per question, median shown. SerpApi got `no_cache=true`, because by default it serves an
identical search from its cache for an hour and that would flatter the time. All calls ran between
14:00 and 14:17 UTC on free tiers. Makcorps is not in the timings: its sign-up wants a username
and password, and I only signed up where Google sign-in was offered. The Booking.com Demand API is
not in them either, because it needs a partner contract.

Every call's start time, wall time and status is in
[the per-call timings file](/benchmarks/hotel-rates-api-benchmark-2026-10-07.json), 63 calls in all.

## Speed and results

| API (what it reads) | Lisbon search, median | rows | sorts by price | cheapest row, 3 nights | one named hotel: calls, median |
| --- | --- | --- | --- | --- | --- |
| StayAPI (Booking.com) | 1.1 s, plus 0.8 s once to look up the city ID | 25 | no | $147.67, tax not stated on the row | 2 calls (ID lookup, then prices); 2.5 s for the prices call |
| SearchApi (Booking.com) | 1.9 s | 15 to 20 | yes | $51 + $30 taxes listed | 2 calls for the room list (a search for the URL, then the property); 3.0 s for the property call |
| HasData (Booking.com) | 2.1 s | 25 | yes | $50.97 + $30.07 taxes listed | 2 calls for the room list (a search for the URL, then the place); 3.2 s for the place call |
| SerpApi (Google Hotels) | 2.4 s | 18 | yes | $78 with taxes ($73 before) | 1 call by name; 2.5 s |
| FlightPowers, mine (Booking.com) | 7.9 s | 15 to 25 | **no** that day, Booking's popularity order; fixed since (see below) | $203 to $257 with taxes, cheapest of the rows it returned | 1 call by name; 10.2 s |
| Apify `voyager/booking-scraper` | 75 s, including the actor start | 20 | asked (`sortBy: price`), rows came back unsorted | $40.52, but that row is one bed in a 10-bed dorm priced for 1 person on a 2-adult search | 1 run by name; 39 s (one run) |
| Xotelo (TripAdvisor rates) | 0.7 s, but the list takes no dates | 30 | n/a | n/a, static price ranges | by TripAdvisor key; 0.7 s, per-night rates from 3 sellers |

The two cheapest Booking.com rows in Lisbon were the same dorm bunk at Samps Hostel on SearchApi
and HasData, $51 before tax and $81 after. SerpApi reads Google Hotels, which is a metasearch
across many sellers, so its Lisbon list is a different set of hotels and not a like-for-like row.

SearchApi's and HasData's search also take a hotel name (SearchApi put Hotel Sant'Angelo first when
I searched it by name), so a single row price for a named hotel is one call there too; the second
call in the table is for the full room list.

## One room, three prices

Hotel Artemide, Basic Double Room, 20 to 23 November 2026, 2 adults:

| Where the number came from | before tax | tax | the number you get back |
| --- | --- | --- | --- |
| HasData, Booking.com US view | $914.64 | 10% VAT $91.46 + city tax $50.65 | total $1,056.76 |
| StayAPI, `country_market=US` | $914.64 | $142 listed as not included | `total_price` $914.64 |
| StayAPI, `country_market=DE` | $919.14 | $142.57 listed as included | `total_price` $1,061.71 |
| SearchApi property call | | no tax field on the room rows | $915 |
| FlightPowers, `proxy_country=us`, 3 runs | | | $1,057, $1,057, $1,057 |
| FlightPowers, `proxy_country=de`, 3 runs | | | $1,062, $1,028, $1,028 |
| SerpApi, Booking.com seller row, `gl=us`, 5 runs | | | $1,050 three times, then $1,034 twice |
| SerpApi, cheapest of 34 sellers | $812 | | $888 (Priceline) |

Almost all of the spread between $915 and $1,062 is tax display, not a different rate.
Booking.com's US view shows the room before tax and adds VAT and city tax at the end; the German
view folds them in. So StayAPI's `total_price` means "before tax" in one market and "after tax"
in the other for the same room. Their docs warn that the market can change tax inclusion, and
the tax breakdown says which way it went, so a careful client can fix it,
but a dashboard that compares the field across markets will invent a 16% gap that isn't there.

If you are comparing hotel APIs, or comparing countries, compare the tax-inclusive total.

## Does the country change the rate?

A little, on this hotel. StayAPI's before-tax figure was $919.14 from Germany and $914.64 from the
US, 0.5% apart. Mine, with the tax folded in on both, read $1,028 from Germany on two of three
runs and $1,057 from the US on three of three, under 3% apart. That matches what I found when I
sampled three hotels from several countries in August: gaps are real but modest, they depend on the
property, and one reading per country measures the noise as much as the market
([the sampled version](/guides/hotel-prices-by-country-api)).

Which APIs let you ask: mine (`proxy_country`, a residential exit in that country), StayAPI
(`country_market`, which their docs call "a request value, not verified geography") and SerpApi on
Google Hotels (`gl`). The Booking.com engines at SearchApi and HasData had no country input; both
sell a Google Hotels engine with `gl` separately.

## Where mine loses

1. **Speed.** 7.9 s on the search and 10.2 s on a named hotel, against 1.1 to 3.2 s for the four
   other APIs. Each call loads Booking.com through a residential proxy in a real browser, and that
   is the cost of it.
2. **No price sort on the test day.** Results came in Booking's popularity order: I sent
   `"sort": "price"` and the API took it without an error and ignored it. That was a bug, fixed
   later the same day: `/v1/hotels/search` now passes `sort` (`price_asc`, `price_desc` or
   `rating_desc`; `"price"` works too) to Booking's own sorter and re-orders the rows on the
   tax-inclusive total. On 2026-10-12 the same Lisbon search with `"sort": "price_asc"` came
   back cheapest first: 20 rows, $81 to $133 for the 3 nights, starting with the same Samps
   Hostel dorm bunk that SearchApi and HasData listed at $81 after tax.
3. **Row count moves.** 15, 25 and 15 rows on three identical calls. HasData and StayAPI returned
   25 every time and both page.
4. **No tax breakdown.** You get one tax-inclusive total. HasData and StayAPI itemise VAT and city
   tax, which a parity tool needs.
5. **A named hotel returns one room.** The full room list is a second endpoint
   (`/v1/hotels/rooms`, 8.9 s), and in one of three default runs the by-name call returned a
   different room than the other two.
6. **The number moves between calls.** Without `proxy_country`, each call can leave from a
   different country's residential IP: the Basic Double read $935, $1,011 and $1,062 on three calls
   to the room list. Pinning a country helps but doesn't settle it: `proxy_country=us` read $1,057
   three times out of three, `proxy_country=de` read $1,062, $1,028 and $1,028.
7. **Per request, two are cheaper.** HasData and SearchApi cost less per call at their entry plans.
   What mine has is the smaller ticket: ${HOTEL_PLANS[1].priceMonthly} to start, against $40, $49
   and $59.
8. **One source.** Mine reads Booking.com only. SerpApi returned 34 sellers for Artemide in one
   call.

## Which one I'd pick, by job

- **Fast Booking.com search at volume:** SearchApi or HasData. Both show the tax on the search rows, both are cheaper per call than mine.
- **One hotel across many sellers:** SerpApi's Google Hotels engine.
- **Reviews, photos and property details on top of rates:** StayAPI.
- **A hotel by the name a person types, one tax-inclusive total, from a country you choose, for
  ${HOTEL_PLANS[1].priceMonthly}:** mine. It's also on the same key as live Google Flights fares,
  if you need both.
- **Free and good enough for a hobby script:** Xotelo's rates endpoint, if you can get the
  TripAdvisor key.
- **Selling the room:** the Booking.com Demand API, through a partner contract.
