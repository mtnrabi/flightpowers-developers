# Booking.com API alternative: live rates without approval

<GuideDates published="2026-10-07" updated="2026-10-18" />

**Short answer:** Booking.com's own Demand API is for approved Managed Affiliate Partners
and its Connectivity APIs are for software that manages properties, so if you need an API
for live Booking.com hotel prices without a partner contract, you use a hosted rates API. Mine, FlightPowers'
Booking Live API, is self-serve on RapidAPI: it returns the live Booking.com rate for a hotel
by the name a person would type, or the properties for a destination and dates, and
`proxy_country` prices the stay as seen from a country you choose. The free BASIC plan is{' '}
{HOTEL_PLANS[0].quota} searches a month and PRO is ${HOTEL_PLANS[1].priceMonthly} for{' '}
{q(HOTEL_PLANS[1])}. It reads Booking.com only and it does not book.

I run FlightPowers, so read this as a vendor writing about his own API. The other providers
below are quoted from their own pages, dated, including where they beat mine.

## Demand API or a rates API: which one do you need?

It depends on whether your product sells the stay or reads its price.

| You want to | Use | The gate |
| --- | --- | --- |
| Sell Booking.com stays and earn commission | Booking.com Demand API | Managed Affiliate Partner contract; Partner Centre access from an account manager |
| Manage your own properties' rates and reservations | Booking.com Connectivity APIs | Built for channel managers and property software |
| Show, watch or compare live Booking.com prices | A hosted rates API, such as mine | A key; mine is on RapidAPI, no contract and no traffic minimum |

The Demand API terms are the ones in
[how to get Booking.com API access](/guides/booking-com-api-key), read from
developers.booking.com on 2026-10-06. Nothing there is a criticism: these are partner
programmes for companies that sell or manage stays. If your product has to complete the
reservation itself, the Demand API is the right road and this page is not.

## What makes a Booking.com rates API reliable?

You can test any provider in an afternoon, FlightPowers' Booking Live API (mine) included.
Three checks:

1. **Live or cached.** A rate read from a snapshot can be hours old. Mine runs the search
   on Booking.com at request time and serves nothing from a cache, and every destination
   search row carries `retrieved_at`.
2. **A name lookup that tells you what it matched.** The quiet failure in hotel data is the
   wrong property: a similar name, the same chain in another city. `/v1/hotels/by-name`
   echoes back the name it resolved to, and `area` (a city or region such as "Antalya")
   steers a common name to the right town.
3. **Sold out looks different from an error.** On mine a sold-out or unknown hotel comes
   back in the same shape with `available: false` and nulls in the price fields, so your
   code checks one boolean instead of guessing what an empty answer meant.

Then run your own hardest hotels on the free plan. {HOTEL_PLANS[0].quota} searches is
enough to see whether the names resolve and the rates match what you see on Booking.com.

## A first request

The rate for one hotel by name, as a German visitor would see it, through
`api.flightpowers.com` (the same call is `POST /hotel_by_name` on
`booking-live-api.p.rapidapi.com`):

```bash
curl -X POST https://api.flightpowers.com/v1/hotels/by-name \
  -H "Content-Type: application/json" \
  -H "x-api-key: $RAPIDAPI_KEY" \
  -d '{
    "hotel_name": "Kremlin Palace",
    "area": "Antalya",
    "checkin_date": "2027-04-12",
    "checkout_date": "2027-04-15",
    "currency": "USD",
    "proxy_country": "de"
  }'
```

The answer is one flat object: the property name, `available`, the `price` for the whole
stay with its `price_string`, `nights`, the room type, the review score and count, and a
`link` that opens the property on Booking.com with your dates filled in. A captured response
is on [the hotel by name reference](/hotels-api/by-name). For a city instead of one hotel,
`/v1/hotels/search` takes a `destination` and returns the properties with live rates and 24
documented filters ([destination search](/hotels-api/search)).

Swap `"de"` for `"jp"` or `"us"` to see another market. Ask each market several times before
you trust a gap, because rates can move between identical requests; the sampled version is in
[do hotel prices change by country?](/guides/hotel-prices-by-country-api).

The same lookups run as tools in Claude, ChatGPT or Cursor through the hotels MCP server at{' '}
<code>{LINKS.mcpHotels.replace('https://', '')}</code> on the same key, where the country
parameter is called `price_as_seen_from`. With no key at all, the free MCP server with ads at{' '}
<code>{LINKS.mcpFree.replace('https://', '')}</code> runs the hotel tools after a Google
sign-in (50 searches a day, without the country parameter).

## When another provider fits better

Read from their own pages on **2026-10-07**. If their page disagrees with this one today,
believe their page.

- **You need more than Booking.com, or reviews and photos.** StayAPI's Booking.com API
  covers search, live rates per room type, reviews, photos and property details, and its
  rates and search take a country `market` too; its menu also lists Airbnb, Agoda,
  TripAdvisor and Google tools. 50 free requests on signup, then $49 a month for 1,500 and $149
  for 10,000. It covers more sources than mine does.
- **You want the lowest price per search at volume.** SearchApi has a Booking.com engine on
  one flat ladder: 100 free requests, then $40 a month for 10,000 searches, which their page
  prints as $4 per 1,000. That is cheaper per search than my PRO plan; the difference is the

- **You sell the room.** That is the Demand API, or a booking platform.
